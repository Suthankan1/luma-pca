Making LUMA fast without changing the hosting

Physics Cube Academy · analysis and implementation plan · 17 Nov 2026 · keeps Vercel, the Oracle VM and Supabase exactly as deployed

Why it is slow. One click travels across the world several times, and the code makes that trip more often than it needs to. The page is built by a Vercel function in Washington DC. That function asks the backend in Hyderabad for data, and the backend asks the database in Tokyo, one question at a time. A page asks in 2 to 5 rounds, one after another. One request for a class's attendance asks the database 20 questions in a row. Locally all of this takes milliseconds; across these distances it takes seconds. Nothing appears on screen meanwhile, so the app looks frozen.

What we can do without moving anything. We can't make the distances shorter, so we make fewer trips. Ask each server fewer times, in fewer rounds, and show the page frame instantly while the data arrives.

The cost model

click time ≈ (rounds of backend calls × ~0.46 s) + (longest chain of database queries × ~0.115 s) + render

Both multipliers are fixed by the hosting. Everything in this plan lowers the two counts: rounds and queries in a chain.

Implementation plan

Ordered by gain for the effort. Every step is a code or app-setting change in the repository, deployed through the existing pipelines. No hosting, region or database move.

Step 1 — Instant feedback on every click

Fixes 1, 12 · frontend · about half a day · users notice it at once

  • Add loading.tsx to /staff, each staff section and /student. It shows the page frame with grey placeholder blocks the moment a link is clicked, while the data streams in.
  • Split heavy pages into <Suspense> sections (class page: details first, then attendance, then engagement), so the fast parts appear first.
  • Turn link prefetching back on for the navigation. Dynamic pages prefetch only their loading frame, which is cheap.
  • Disable buttons while a form submits (most already do) so double clicks don't double the load.

Step 2 — Remove the "who am I" round trip

Fix 2 · frontend · about half a day · saves ~0.5 s on every page

  • At sign-in and every token refresh, store the person's identity (account, academy, roles) in the existing sealed, HttpOnly session cookie. Pages read it locally instead of calling /auth/me.
  • Safe because the backend still checks the account, session and roles on every data call. A removed role takes effect on the next data call, and on screen at the next token refresh (at most 10 minutes).
  • Until then, a quick version: start the page's data calls at the same time as /auth/me instead of after it.

Step 3 — One round per page

Fixes 3, 5 · frontend and backend · 1–2 days · saves 0.5–2 s on the batch page, Zoom review and the class page

  • Batch page and Zoom review: issue every call at once (Promise.all), not one after another.
  • Add page-shaped backend endpoints that return everything a page needs in one response: GET /api/v1/pages/class/{id} (class, expected students, attendance, engagement, linked runs) and GET /api/v1/pages/batch/{id} (batch, roster, assignments, summary). Access rules stay in the services they call.
  • Staff home: one GET /api/v1/pages/staff-home for today's classes and the attention counts.

Step 4 — Fewer database round trips per request

Fix 4 · backend · 2–3 days · the class attendance request goes from ~2.3 s to ~0.5 s

  • Class attendance: 20 → about 4 queries. Load the session, expected students, linked runs, events and report rows with set-based SQL (= ANY(?), joins, json_agg) instead of one query per step.
  • Engagement 9 → 2, Zoom matching 7 → 2, roster 6 → 2, by the same approach. Each change gets a test that pins the query count (the counting probe used for this report), so it can't creep back.
  • Read-only requests run in one transaction with no extra round trips for setup and commit.

Step 5 — Remember what rarely changes

Fix 7 · backend · 1 day

  • An in-memory cache in the backend for courses, batches, the attendance rule, engagement settings and staff names. It lasts 60 s, is cleared immediately by any change to that data, and is per academy. Only data that every manager may see, never student records or anything personal.
  • Saves 3–6 Tokyo queries on most pages.

Step 6 — Fix the security gap, keep the speed

Fix 14 · backend · half a day · do it with step 2

  • Clear the 15-second sign-in cache entry the moment someone signs out, signs out everywhere, is disabled, changes password or changes role. Add a test that a disabled account is refused on the very next request.

Step 7 — Make the small VM go further

Fixes 6, 8, 9 · backend settings · half a day

  • Database pool: keep connections for 30 minutes (max-lifetime: 1800000), idle 10 minutes, keep-alive ping every 2 minutes, about 8 connections. Supabase's pooler keeps them alive.
  • Java virtual threads (spring.threads.virtual.enabled: true). Waiting for Tokyo then costs almost no memory or CPU, so 7 parallel requests don't crowd out each other.
  • Background workers: poll every 5 s only while there is work, slowing to 30–60 s when idle (Zoom receipts, invitation emails).
  • JVM flags for 1 GB: -XX:+UseSerialGC -Xss512k -XX:MaxMetaspaceSize=128m, so it fits in memory and doesn't swap.

Step 8 — Lighter saves and live pages

Fixes 10, 11, 13 · frontend · 1 day

  • After a save, refresh only the part that changed (a narrow revalidatePath or the action's own result), and show the change at once with useOptimistic.
  • Live class page: refresh only attendance and engagement through one small endpoint every 30 s, not the whole page.
  • Backend calls wait up to 10 s; after 3 s the page says "Still loading…" instead of failing.

Step 9 — Measure, then keep it fast

All · 1 day

  • A Server-Timing header from the web app (time per backend call), visible in the browser's developer tools.
  • The same curl probes and a k6 run against the live site, before and after each step (50, then 200 users).
  • Query-count tests in CI for the page endpoints. A test fails if a page needs more than one backend round.
