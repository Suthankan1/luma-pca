LUMA speed, caching and email: the full implementation plan

Physics Cube Academy · 18 Nov 2026 · for the current hosting (Vercel, Oracle VM in Hyderabad, Supabase in Tokyo), unchanged

Where things stand. PRs #100 and #101 did real work: identity now comes from the session cookie, queries are batched in Zoom matching, some reference data is cached, Java uses virtual threads, and the connection pool stays warm. Two of those changes also undid speed, though:

  • 9 of the 12 loading screens were removed (to keep redirect and 404 status codes exact). In Next.js 16 a dynamic page without a loading screen gets no instant feedback and is never prefetched. So most clicks are blank again until the page is ready.
  • The sign-in check cache was removed (to close the 15-second security gap). The gap is closed, but every backend call now pays two extra database queries to Tokyo (~0.25 s).

Both can be restored safely; tracks A and B below show how.

Track A — Instant feedback (do first)

A1. Bring the loading screens back without breaking redirects

frontend · fixes the blank-click problem and re-enables prefetching for dynamic pages

  • Move requirePortal into app/staff/layout.tsx and app/student/layout.tsx. Identity comes from the cookie now, so this costs no backend call, and a layout redirect runs before any streaming starts. Signed-out visitors get a real 307 again.
  • Check the ID format (uuidOrNull) in the layout of each [id] segment and call notFound() there, so malformed links still get a real 404.
  • Then put loading.tsx back on every section (StaffSkeleton already exists). Only a well-formed ID that doesn't exist renders "Page not found" with status 200, because it's discovered while streaming. Update the two tests that assert 404 for that case to check the page text instead.

A2. Show that a click was registered

frontend · small

  • Navigation links use useLinkStatus() (built into Next.js 16) to show a subtle pending state on the clicked item.
  • A thin progress bar at the top of the page during any navigation or form submission.
  • Buttons say "Saving…" and are disabled while a form submits (most already do; make it universal).

A3. Let the browser keep pages it has seen

frontend · next.config.ts

  • experimental.staleTimes = { dynamic: 30, static: 180 }. Going back to a page seen in the last 30 s is instant, with no server trip. Server actions that change data already call revalidatePath, which clears that page.
  • Keep prefetching on for the main navigation (it prefetches the loading screen, which is cheap). Turn it off only for long lists of links, such as rosters, to avoid flooding.

Track B — Caching, layer by layer

4 · DatabaseFewer round tripsSet-based queries instead of one per row——

Rules for every layer. Cache keys always include the academy, and the account where results depend on assignments (instructors see only their batches). Student personal data is never shared between people, and no cache sits in front of a write. A cache that can't be cleared on the event that changes the data has no place in sign-in or attendance.

B1. The sign-in check cache, done safely

backend · saves ~0.25 s on every backend call

  • Restore the per-session cache (account, roles, session state) for 60 s, and clear it through one AuthCacheEvictor called from sign-out, sign-out everywhere, disable, role change, password change, password reset and refresh-token reuse.
  • Tests for each event: the very next request after it is refused (the tests from #100 already cover the cases).

B2. Reference data

backend and frontend

  • Backend: extend the existing 60 s caches (courses, rule) to batches, engagement settings and staff names, with the same write-time clearing.
  • Frontend: wrap the reference-data fetches used by forms (batch pickers, course lists) in 'use cache' keyed by academy and role. Pages then skip that backend call entirely. This needs cacheComponents: true; adopt it page by page.

B3. Final attendance

backend

  • A final class's attendance only changes by correction, recalculation or an appeal decision. Cache the computed view per class until one of those happens. Exports, batch summaries and the student portal then answer from memory.
  • Provisional (live) attendance: a 10-second cache, so a full class of refreshing screens costs one computation.

Track C — One backend call per page

C1. Page endpoints

backend and frontend · class page 7 calls → 1

  • GET /api/v1/pages/class/{id}: class, expected students, attendance, engagement, linked runs.
  • GET /api/v1/pages/batch/{id}?from&to: batch, roster, assignments, summary.
  • GET /api/v1/pages/staff-home and GET /api/v1/me/home: today's classes and counts; the student's classes, attendance and consent.
  • Each calls the existing services, so every access rule stays where it is. Added to the OpenAPI contract and its check.

C2. The chattiest requests

backend · each with a test that pins its query count

  • Class attendance 20 → 4, engagement 9 → 2, roster 6 → 2, Zoom matching (partly done in #101) → 2.
  • Method: load related rows together (= ANY(?), joins, json_agg), not one query per step.

Track D — The small VM

  • Zoom receipt worker: poll every 5 s only while receipts are arriving, 60 s when idle (the mail worker is already 30 s).
  • JVM flags for 1 GB RAM: -XX:+UseSerialGC -Xss512k -XX:MaxMetaspaceSize=128m -Xmx400m. Check with free -m and vmstat 1 that swap stays unused while a page loads.

Track E — Email through Gmail

E1. The code change (needed: Gmail requires STARTTLS)

The backend has no SMTP TLS settings today. On port 587, Gmail refuses mail unless the connection is upgraded with STARTTLS, so sending fails even with correct credentials. Add to application.yml:

spring.mail.properties.mail.smtp.auth: true
spring.mail.properties.mail.smtp.starttls.enable: true
spring.mail.properties.mail.smtp.starttls.required: true
spring.mail.properties.mail.smtp.connectiontimeout: 10000
spring.mail.properties.mail.smtp.timeout: 10000
spring.mail.properties.mail.smtp.writetimeout: 10000

The timeouts keep a slow mail server from tying up the VM's two mail threads.

E2. The Gmail account

  1. Use a dedicated academy Gmail account for sending, not a personal one.
  2. Turn on 2-Step Verification, then create an App password (Google Account → Security → App passwords). It is a 16-character code; the normal password does not work for SMTP.

E3. The environment (on the Oracle VM: the backend sends the mail, not Vercel)

VariableValue

Put these in the environment file the luma-backend systemd service loads on the VM, then sudo systemctl restart luma-backend. Keep the file readable only by the service user (chmod 600). The app password goes on the VM and nowhere else: never in Git, chat or Vercel. Enter it yourself; it is a credential.

E4. Limits to plan around

  • A personal Gmail account sends to about 500 recipients a day; Google Workspace about 2,000. Over the limit, Gmail answers "Daily sending quota exceeded" (550 5.4.5) for a day. Inviting all 500 students at once would use a whole day's quota: invite batch by batch, or use Workspace.
  • Failed sends already retry with back-off and show up under "failed invitations"; the backend log says "email for account … failed" (search it with journalctl -u luma-backend | grep "email for account").

E5. Check it works

  1. journalctl -u luma-backend -n 50 after the restart: no mail configuration errors.
  2. Sign-in page → "Forgot your password" for a staff account you control. The email arrives within a minute; the link opens luma-pca.vercel.app and works once.
  3. Invite one test student from their record, then check the inbox and spam folder (mark "not spam" once).

Track F — Measure and guard

  • The web app sends a Server-Timing header (time per backend call), visible in the browser's network panel.
  • A dedicated test staff account (an instructor on a test batch, no real students) so pages can be timed from outside. The same probe runs before and after every step.
  • CI: query-count tests for the page endpoints, and a test that fails if a page makes more than one backend round.
  • Targets: feedback after a click under 0.1 s; revisited pages instant; first open of the class page p95 under 1.5 s.
